# Cartographer v1 spec

This is the contract for v1. It turns the decisions indexed on the wayfinder map (issue #1) into formats and commands. Where it adds a detail the map left open, the detail is marked **(spec)**. Vocabulary is in `GLOSSARY.md`.

## 1. Boundary

In v1, built in this order:

1. **Atlas core**: entry format, validation, generated indexes and reverse lists, open questions, read-only queries, rename.
2. **Mechanical pass**: extractors for .NET (SDK-style and legacy, C# and VB), config files (connection strings, WCF), VB6, classic ASP, ADO calls, and SQL Server schema sources (SSDT, loose and numbered scripts).
3. **Scan sessions**: scan state, changed files to components, what is due, one commit per repository with a change summary, local-only or pull request.
4. **SCM access**: listing on GitHub and Azure DevOps, cached partial clones, linking locations.
5. **Live database introspection** for SQL Server, with drift.
6. **Site**: an Astro site with a map of clusters, a page per cluster, an Everything table with search, entries, data tags, questions and recent changes (ADR 1).
7. **Skills and plugins**: scan, work open questions, ask the atlas, set up an atlas; Claude Code and GitHub Copilot plugins.

Staged after the first v1 release, in this order:

1. On-demand Roslyn usage analysis for SDK-style projects.
2. Release-branch differences (the `branches:` section on entries). v1 tracks the default branch only.
3. Readers for EF Core snapshots, EDMX, `.dbml`, typed DataSets, SSIS packages, SQL Agent jobs and linked servers.
4. The clone cache size cap (v1 has `cache clear` only).
5. `db replay <repository>`: run a repository's migrations (Flyway, numbered scripts) into a throwaway SQL Server container and read the schema from it. Like Roslyn, it runs repository code, so it is only ever an explicit command on a named repository.

Out of scope: see the map.

## 2. Atlas layout

```
<atlas>/
├── cartographer.yml                 config (section 9)
├── AGENTS.md                        how to navigate
├── repositories/<project>-<repo>/
│   ├── repository.md
│   ├── scan-state.yml
│   └── components/<component>.md
├── databases/<database>/
│   ├── database.md
│   ├── scan-state.yml               only when a live instance has been read
│   ├── tables/<schema>/<table>.md   tables and views
│   ├── routines/<schema>/<routine>.md
│   └── triggers/<schema>/<trigger>.md
├── systems/<system>.md
├── channels/<channel>.md
├── external/<external-system>.md
├── flows/<flow>.md
├── changes/<date>-<repository>-<commit7>.md   change summaries, written by the CLI
├── clusters.yaml                    pinned clusters, written by the CLI (ADR 1)
└── _generated/                      committed; safe to delete and rebuild
```

- An entry's ID is its path without `.md`, with `/` separators. All path segments are lower-case `[a-z0-9._-]`. **(spec)** Other characters become `-`.
- `kind` must agree with the path: `repositories/*/repository` is a repository, `repositories/*/components/*` a component, `databases/*/database` a database, and so on.

## 3. Entry format

One Markdown file: YAML frontmatter, then the body. Unknown frontmatter keys are an error. Empty lists and empty sections are left out. Dates are quoted `"YYYY-MM-DD"`.

### Frontmatter keys, in this order

| Key | Kinds | Meaning |
|---|---|---|
| `kind` | all | `repository`, `component`, `database`, `table`, `view`, `routine`, `trigger`, `system`, `channel`, `external`, `flow` |
| `name` | all | The real name as written in the source, original capitalisation. |
| `type` | component, routine, channel | Component: `library`, `service`, `site`, `desktop-app`, `job`, `etl`, `report`. Routine: `procedure`, `function`. Channel: `queue`, `topic`, `file-drop`. |
| `summary` | all | One line, at most 200 characters. |
| `status` | any | `retired` when the thing is gone but kept so links resolve. |
| `repository` | component | ID of the owning repository. |
| `database` | table, view, routine, trigger | ID of the owning database. |
| `engine` | database | `sqlserver`, or another engine's name (no schema reading for those). |
| `stack` | repository, component | List of technologies seen, e.g. `[csharp, net8.0]`, `[vb6]`, `[classic-asp]`. |
| `locations` | repository | List of `{id, primary}`. `id` is `github:<org>/<repo>` or `azdo:<org>/<project>/<repo>`. |
| `aliases` | database | Other names and name patterns the database is known by. |
| `instances` | database | List of `{name, environment, read, permission}`; `read` is the date of the last successful live read, `permission` is `full`, `definitions` or `limited`. |
| `sources` | all | Map of short key to evidence pointer. Declared once; cited by key. |
| `provides` | component | List of `{name, as, basis, source}`. `as` is `nuget`, `assembly`, `progid`, `typelib`, `namespace`, `contract`, or `package` for any other ecosystem's package name (a WCF service contract). |
| `systems` | component, database | List of `{id, basis, source}`. |
| `tags` | table, view | List of `{name, basis, source}`. |
| `owner` | all | `{name, basis, source}`. |
| `packages` | component | Public packages used, plain strings `"<name> <version>"`. |
| `links` | all | List of links (below). |
| `drift` | database, table, view, routine, trigger | List of `{what, sources}`: a disagreement and the sources that disagree. |
| `verified` | all | `{commit, date, cartographer}`; for live-only entries `commit` is left out. |

### Links

```yaml
links:
  - type: depends-on
    to: repositories/acme-core/components/acme-core
    name: Acme.Core            # the provided name the reference was made against
    version: "2.1.0"
    uses: [OrderClient, Money] # library types used
    count: 14                  # usage sites
    basis: extracted
    source: proj#L32
```

| Type | From | To | Extra keys |
|---|---|---|---|
| `depends-on` | component | component | `name`, `version`, `uses`, `count` |
| `calls` | component, routine, trigger, view | component, routine | `how` (`http`, `wcf`, `com`, `sql`), `via` |
| `reads`, `writes` | component, routine, trigger, view | table, view | `via` |
| `uses` | component | database | |
| `publishes-to`, `consumes-from` | component | channel | `via` |
| `sends-to`, `receives-from` | component | external | `via` |
| `links-to` | database | database | |
| `references` | table | table | `name` (constraint name) |
| `fires-on` | trigger | table, view | |
| `defines` | repository | database | |

- `via` is the ID of the library a link was reached through.
- A link has `to`, or it is **unresolved**: no `to`, a `name`, and optionally `database` (a database name hint). The resolver (section 6) fills `to` when a target appears.
- `basis` is `extracted`, `inferred` or `stated`. Required on every link, provided name, system membership, tag and owner.

### Evidence pointers

- In `sources`: `<repository>:<path>@<commit7>` where `<repository>` is the repository folder name, or `instance:<instance name>@<date>`, or `person:<who>@<date>`.
- On a fact: `<key>` or `<key>#L<n>` or `<key>#L<n>-L<m>`, where `<key>` is in the entry's `sources`; or a full pointer with optional `#L…` when the evidence is in a file the entry does not declare.

### Body

Fixed sections, in this order, each left out when empty:

```markdown
## Overview
Plain language.

## Technical detail
<!-- extracted -->
Written and replaced by the CLI: columns, parameters, target frameworks.
<!-- /extracted -->
Agent prose.

<!-- person -->
A passage a person owns. Agents and the CLI leave it alone.
<!-- /person -->

## Open questions

### q1

- State: open
- Raised by: cli
- Attempts: 0
- Missing: Which component provides the package Acme.Logging.
- Waiting on: name Acme.Logging
- Answer looks like: A component whose provides list contains Acme.Logging, or a person stating it is public.
- Answer:

### Dismissed

- Whether PolySharp is a run-time dependency: no, it is build-time only.
```

- States: `open`, `needs-person`, `answered`, `dismissed`. `Raised by`: `cli`, `agent`, `person`.
- `Waiting on`: `repository <id>`, `name <provided name>`, `entry <id>` or `person`.
- **(spec)** An open question moves to `needs-person` after 3 failed attempts. The CLI warns when an entry has more than 5 questions, when it is longer than 300 lines, and when it was last verified more than 180 days ago.
- A question is a duplicate when another on the same entry has the same `Missing` text, ignoring case and spacing.

### Secrets

Validation rejects an entry containing something that looks like a credential: `password=`, `pwd=`, `secret=`, `token=`, `accountkey=`, `sharedaccesskey=` followed by a value, or a private key header. Extractors record `server` and `database` from a connection string and nothing else.

## 4. Generated files

All under `_generated/`, rebuilt by `cartographer index`:

- `index.md`: the root index: each top-level folder with its entry count.
- `<folder>/index.md` for every folder holding entries: sub-folders with counts, then a row per entry directly in it (ID, kind, name, summary). More than 200 rows are split into `index-1.md`, `index-2.md`, … and the index lists those with their ranges.
- `<entry id>.used-by.md`: direct inbound links, grouped by link type; for a system, its members.
- `open-questions.md`: every question, grouped by state, `needs-person` first.
- `provided-names.md`: every provided name and the component that provides it.

Output is deterministic: sorted by ID, no timestamps.

## 5. Scan state

`repositories/<repo>/scan-state.yml`, written by the CLI:

```yaml
repository: repositories/acme-billing
cartographer: 0.1.0
locations:
  - id: github:acme/Finance-billing
    primary: true
    gone: false
    tip: <full sha>
    seen: "2026-11-21"
branches:
  main:
    role: default
    scanned-commit: <full sha>
    scanned: "2026-11-21"
entries: [repositories/acme-billing/components/billing-api]   # entries this repository's mechanical pass owns
in-progress:            # present only while a scan is incomplete
  branch: main
  commit: <full sha>
  mode: full            # full | changed
  components: {billing-api: done, billing-web: pending}
```

A repository is due when: its default branch tip differs from `scanned-commit`; the CLI's major version changed; it has an open question whose `Waiting on` target changed in this atlas since its last scan; it has never been scanned; it was last scanned more than `limits.scan-age-days` ago (90 by default) **(spec)**; or `in-progress` is present.

## 6. Mechanical pass

`cartographer scan` runs every extractor over a checkout and merges the result into the atlas.

- Extractors emit entries holding only extracted facts. They never read outside the checkout, never run anything from it, and treat its text as data.
- **Components.** A component root is the directory of a project file (`.csproj`, `.vbproj`, `.fsproj`, `.vbp`), or the top-most directory of a run of `.asp` files outside any project. A file belongs to the nearest component root above it. Component type comes from the project (output type, SDK, web markers); when it cannot be told, `library`.
- **Merge.** For an existing entry the CLI replaces everything with basis `extracted` and the `<!-- extracted -->` block, and leaves inferred and stated facts, prose and person passages alone. `name` and `summary` are written only when the entry is created. An entry the pass owned that is no longer produced is marked `status: retired`, never deleted.
- **Resolver.** After a merge, across the whole atlas:
  - a `depends-on` whose `name` is provided by a component gets its `to`;
  - one that matches a prefix in `internal-prefixes` and has no provider stays unresolved and gets a CLI question (`Waiting on: name <name>`);
  - a file name (`.dll`, `.ocx`, `.tlb`, `.exe`), a type-library GUID, or a COM or WCF call that nothing provides also stays unresolved with a CLI question, unless a Dismissed note on the entry names it;
  - names are matched by kind: a `depends-on` against `nuget`, `assembly` and `typelib` names, a COM call against `progid`, a WCF call against `contract` (falling back to the interface's short name);
  - an unresolved `uses` is matched against database names and aliases;
  - anything else is public and moves to `packages`. On every run `packages` is checked again, and a name that has gained a provider is promoted back to a `depends-on` link.
  - an unresolved `calls`, `reads` or `writes` with a `name` is matched against routines and tables by schema-qualified name, within the hinted database if one is given, otherwise across all; exactly one match resolves it.
  - a link whose `to` no longer exists, or exists with `status: retired`, raises a CLI question on the entry holding the link (`Waiting on: entry <id>`).
- **Databases from repositories.** `.sql` files are parsed, never run; the repository gets a `defines` link to each database it defines. Tables carry `references` links, triggers get entries with `fires-on`, and routines, triggers and views carry `reads`, `writes` and `calls` found by parsing their bodies. A target defined in the same database in the same pass gets `to`; any other is left unresolved with its `schema.name` and, from a three-part name, a `database` hint. Dynamic SQL is counted, not followed. **(spec)** Which database a `.sql` file is for, first rule that applies:
  1. a file under the directory of a `.sqlproj` (the nearest one above it): the database named by the `.sqlproj` file name;
  2. the `USE <name>` in effect at the file's first definition (its last `USE` when it defines nothing), otherwise its `CREATE DATABASE <name>`; `master`, `tempdb`, `model` and `msdb` are ignored;
  3. the name that the other files in the same directory give by rule 2, when they all give the same one;
  4. for a file that defines something, the name of the nearest directory common to all defining files that reach this rule, or the repository folder name when that directory is the repository root. A file that defines nothing joins that database if there is one, and is otherwise ignored.

  A database is created only when at least one of its files defines something. Its files are applied in path order, digit runs compared as numbers (`2_x.sql` before `10_x.sql`), so `CREATE`, `ALTER` and `DROP` add up to the final schema. A file with only data statements or nothing parseable defines nothing; such files and files with parse errors are counted in the database entry's extracted block. A database project is not a component.
- **Generic repositories.** A repository with no recognised project still gets a repository entry with `stack` (from file extensions and manifest files) and file counts in its extracted block.

## 7. CLI

A dotnet tool named `cartographer`. It never prompts: all input comes from arguments, `cartographer.yml` and environment. Exit code 0 is success, 1 a failed check, 2 a usage or environment error. `--atlas <dir>` on any command; default is the current directory.

| Command | Does |
|---|---|
| `init <dir> --organisation <name> [--github <org>] [--azdo <org>]` | Creates an atlas: config, `AGENTS.md`, `git init` and a first commit. |
| `repos list [--refresh]` | Lists repositories at both SCMs with their linked locations. |
| `repos due` | Lists repositories due for a scan, each with its reason. |
| `clone <repository>` | Fetches or updates the cached partial clone; prints its path. |
| `changed <repository>` | Files changed since the last scanned commit, grouped by component. |
| `scan <repository> [--path <checkout>] [--full]` | Mechanical pass for one repository, then resolve, validate and index. |
| `scan --all [--max <n>]` | Mechanical pass over every due repository. |
| `candidates <repository> --library <component id>` | Text-search candidates for usage sites of a library's namespaces and types. |
| `question add <entry> --missing … --waiting-on … --answer-looks-like … [--raised-by agent]` | Adds a question; refuses duplicates. |
| `question attempt <entry> <q>` | Records a failed attempt; moves to `needs-person` at the limit. |
| `question retry` | Lists open questions whose `Waiting on` target has changed. |
| `check` | Validates every entry. |
| `index` | Rebuilds `_generated/`. |
| `rename <old id> <new id>` | Moves an entry (and what is under it) and rewrites links. |
| `find <text>`, `show <id>`, `used-by <id>`, `impact <id> [--depth n]` | Read-only queries with small output. |
| `done <repository> <component>` | Marks one component's entries complete in the scan in progress. |
| `finish <repository> [--force]` | Refuses while a component is still pending (unless forced). Marks the repository's scan complete, writes its change summary and commits its files on the scan branch. |
| `session start [--branch <name>]`, `session end [--pull-request]` | Creates the scan branch; at the end either leaves it local or pushes and opens a pull request whose description joins the change summaries. |
| `session commit --message <text>` | Validates, reindexes and commits everything changed on the scan branch: a partial scan, answered questions, systems and tags. |
| `db read <instance> [--database <name>]` | Reads live catalogs into entries; records fingerprint, permission level and drift. |
| `db queries`, `db role-script` | Prints the fixed catalog queries, and a script creating a least-privilege role. |
| `clusters [--parts]` | Lists the clusters, the share of links inside them, and a regroup when one is worth making (ADR 1). |
| `clusters pin <name>`, `clusters unpin <name>`, `clusters rename <name> <new name>` | Pins clusters in `clusters.yaml`. A pinned cluster keeps its members and name; renaming pins. Each changes only the cluster named. |
| `clusters pin --all` | Pins every cluster that is not pinned yet. |
| `clusters regroup` | Groups every part afresh and pins the result. A cluster holding more than half of a pinned one keeps its name. |
| `site prepare --out <dir>` | Writes the site data, including the clusters. Never pins. |
| `site build --out <dir>` | Runs `site prepare`, then builds the Astro site. |
| `cache clear` | Deletes the clone cache. |

Credentials: `GITHUB_TOKEN` or `gh auth token`; `AZURE_DEVOPS_EXT_PAT` or `az account get-access-token`; git's own credential helper for cloning; integrated sign-in or `CARTOGRAPHER_SQL_<INSTANCE>` (a connection string) for databases. Nothing is stored.

## 8. Site

- `site prepare` writes one JSON file per entry, plus the clusters, everything, questions, changes and tags lists (shapes in `site/README.md`). The Astro site reads only those files.
- Parts are components, databases, channels and external systems. Clusters group parts by their links (ADR 1); a link to a table, view, routine or trigger counts as a link to its database, and code dependencies (`depends-on`) are left out. Pinned clusters come from `clusters.yaml`; the other parts are grouped afresh on every run.
- The map shows every part, one lane per cluster. Arrows follow the data: `writes`, `publishes-to` and `sends-to` point from the part to the target; `reads`, `consumes-from` and `receives-from` point from the target to the part. Other links between parts (`calls`, `uses`, `links-to`, and `references` or `fires-on` across databases) relate two parts without moving data one way, and are drawn dotted as calls. Within a lane, each part sits one column right of the furthest part in the lane that feeds it.
- Selecting a part lights up everything that feeds it and everything its data reaches. Above 80 parts, lanes of more than 6 parts start closed, with one box per column, and open on demand. Owners and systems are facts on a part's page, never the grouping.
- When a regroup is suggested, the map says what would merge or move and how to apply it (`cartographer clusters regroup`).

## 9. Config

`cartographer.yml` at the atlas root:

```yaml
organisation: Acme
github: {organisation: acme}
azure-devops: {organisation: acme}
allow:                           # optional: only these repositories are listed
  github:
    acme: ["Finance-*", "/^ops-(tools|scripts)$/"]   # organisation: repository patterns
    acme-labs: []                                     # every repository
  azure-devops:
    acme:                        # organisation
      Finance: []                # project pattern: repository patterns
      "Legacy*": ["payroll", "billing-*"]
exclude: ["*-archive", "sandbox-*"]
internal-prefixes: ["Acme.*"]
locations:                       # mappings a person wrote; they win
  repositories/finance-billing: ["azdo:acme/Finance/billing", "github:acme/Finance-billing"]
instances:
  - name: sql-test-01
    server: sql-test-01.acme.local
    environment: test
    production: false            # a production instance is read only when allowed: true
    allowed: true
    databases: [Billing]         # empty means every database the identity can see
limits:
  scan-age-days: 90
  question-attempts: 3
```

Name patterns in `allow` and `exclude` are globs (`*` any run of characters, `?` one, matching the whole name) or regular expressions written between slashes (`/^ops-/`, matching anywhere unless anchored). Case is ignored. Quote a pattern that starts with `*` or `/`, or holds `:`, so YAML reads it as text.

- `allow` lists organisations as well as filtering them: an organisation under `allow` is listed even when `github` or `azure-devops` does not name it. Organisation names are plain names.
- An empty or missing list allows everything below it. An SCM with nothing under `allow` is not filtered.
- A repository `allow` leaves out is reported as `skipped (not allowed)` by `repos list --refresh`, costs no further requests, and keeps its scan state as it was. `exclude` then applies to folder names.

## 10. Skills

Plain skill folders under `skills/`, each a `SKILL.md` with reference files, shipped as one plugin whose root is this repository (`.claude-plugin/plugin.json`), which Claude Code and GitHub Copilot CLI both read:

- `cartographer-scan`: runs a session: `session start`, `repos due`, per repository the mechanical pass then one fresh sub-agent that completes the entries, `check`, `finish`, and `session end`. Never stops to ask: anything it would ask becomes an open question.
- `cartographer-questions`: `question retry`, tries each, folds in answers people wrote as stated facts.
- `cartographer-ask`: answers from the atlas, reading the root index, one folder index, then one entry.
- `cartographer-setup`: creates an atlas and its config.

## 11. Testing

- Fixtures are folders under `fixtures/`; tests turn them into local git repositories.
- What the CLI extracts is compared exactly against stored expected atlases (`fixtures/<name>/expected/`). `CARTOGRAPHER_ACCEPT=1 dotnet test` rewrites them.
- Skills are checked against a list of facts that must be found; this is run by hand, not in CI.
