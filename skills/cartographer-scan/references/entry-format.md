# The entry format

An entry is one Markdown file about one thing: YAML frontmatter, then a body. The CLI parses every entry and rewrites it in a fixed layout, and `cartographer check` refuses an entry that breaks these rules, so write exactly this shape. Two finished entries are at the end of this file.

## Where an entry lives

An entry's ID is its path inside the atlas without `.md`. Every path segment is lower-case `a-z`, `0-9`, `.`, `_` and `-`; any other character in a real name becomes `-`.

| Kind | Path |
|---|---|
| repository | `repositories/<project>-<repo>/repository.md` |
| component | `repositories/<project>-<repo>/components/<component>.md` |
| database | `databases/<database>/database.md` |
| table, view | `databases/<database>/tables/<schema>/<table>.md` |
| routine | `databases/<database>/routines/<schema>/<routine>.md` |
| trigger | `databases/<database>/triggers/<schema>/<trigger>.md` |
| system | `systems/<system>.md` |
| channel | `channels/<channel>.md` |
| external | `external/<external-system>.md` |
| flow | `flows/<flow>.md` |

## Frontmatter

Keys appear in this order. Leave out a key that has nothing in it. A key not in this table is an error. Dates and versions are quoted strings.

| Key | On | Meaning |
|---|---|---|
| `kind` | all | One of the kinds above. Must agree with the path. |
| `name` | all | The real name as written in the source, original capitalisation. For a table, view, routine or trigger it is `schema.Name`. |
| `type` | component, routine, channel | Component: `library`, `service`, `site`, `desktop-app`, `job`, `etl`, `report`. Routine: `procedure`, `function`. Channel: `queue`, `topic`, `file-drop`. Required on a component. |
| `summary` | all | One line, at most 200 characters. |
| `status` | any | `retired`, set by the CLI. Do not set it. |
| `repository` | component | `repositories/<folder>/repository`. |
| `database` | table, view, routine, trigger | `databases/<folder>/database`. |
| `engine` | database | `sqlserver`, or another engine's name such as `oracle` or `access`. |
| `stack` | repository, component | Technologies seen, e.g. `[csharp, net8.0]`, `[vb6]`, `[classic-asp]`. |
| `locations` | repository | Written by the CLI. |
| `aliases` | database | Other names and name patterns the database is known by. |
| `instances` | database | Written by the CLI from live reads. |
| `sources` | all | Map of short key to evidence pointer. Declared once, cited by key. |
| `provides` | component | List of `{name, as, basis, source}`. `as` is `nuget`, `assembly`, `progid`, `typelib` or `namespace`. |
| `systems` | component, database | List of `{id, basis, source}`. |
| `tags` | table, view | List of `{name, basis, source}`: business-data tags such as `customer` or `payment`. |
| `owner` | all | `{name, basis, source}`. |
| `packages` | component | Public packages used, plain strings `"<name> <version>"`. Written by the CLI. |
| `links` | all | The entry's links (next section). |
| `drift` | database objects | Written by the CLI. |
| `verified` | all | `{commit, date, cartographer}`. Written by the CLI. |

## Links

A link is recorded once, on the entry it starts from. What links *to* an entry is generated by the CLI; never write a reverse link.

```yaml
links:
  - type: reads
    to: databases/billing/tables/dbo/customer
    via: repositories/platform-core/components/acme-data
    basis: inferred
    source: payments#L41
```

| Type | From | To | Extra keys |
|---|---|---|---|
| `depends-on` | component | component | `name`, `version`, `uses`, `count` |
| `calls` | component, routine, trigger | component, routine | `how` (`http`, `wcf`, `com`, `sql`), `via` |
| `reads`, `writes` | component, routine, trigger | table, view | `via` |
| `uses` | component | database | |
| `publishes-to`, `consumes-from` | component | channel | `via` |
| `sends-to`, `receives-from` | component | external | `via` |
| `links-to` | database | database | |
| `references` | table | table | `name` (constraint name) |
| `fires-on` | trigger | table, view | |
| `defines` | repository | database | |

- `basis` and `source` are required on every link, provided name, system membership, tag and owner.
- `basis` is `extracted` (the CLI read it mechanically), `inferred` (an agent concluded it from reading code) or `stated` (a person said it). An agent writes `inferred`, except when folding in a person's answer, which is `stated`.
- `uses` is the list of a library's types the consumer uses; `count` is the number of usage sites.
- `via` is the ID of the library a link was reached through.
- `uses` (the link type) is the fallback when only the connection to a database is known and no table or routine can be named.
- **An unresolved link** has no `to`. It has a `name` and, optionally, a `database` name hint. Use it when you know the real name of the table or routine but not its entry: write `name: dbo.Orders` and `database: Billing`, and the CLI fills in `to` when exactly one entry matches. This is safer than guessing an ID.
- Two links on one entry with the same `type`, `to` and `via` are an error. One link per target; cite the clearest evidence.

## Evidence pointers

Every fact says where it was seen, so a reader can check it.

In `sources`, a pointer is one of:

- `<repository folder>:<path>@<commit7>`: a file in a repository at a commit, e.g. `finance-billing:src/Api/Program.cs@1a2b3c4`. No host URL, so the pointer survives a move between SCMs.
- `instance:<instance name>@<YYYY-MM-DD>`: a live database read. The CLI writes these.
- `person:<who>@<YYYY-MM-DD>`: a person said it. `<who>` is a name with no `@` in it.

Source keys are lower-case letters, digits and hyphens. On a fact, `source` is a key (`proj`), a key with a line or range (`proj#L32`, `proj#L32-L40`), or a full pointer with an optional `#L…` when the evidence is in a file the entry does not declare.

Use the commit the scan is working on (the first seven characters of `in-progress.commit` in `scan-state.yml`). When you re-check a fact against a newer commit, update the commit in its pointer.

## Body

Three sections, in this order, each left out when it would be empty. Any other `## ` heading is an error.

```markdown
## Overview

Plain language.

## Technical detail

<!-- extracted -->
Written and replaced by the CLI. Leave it alone.
<!-- /extracted -->

Agent prose.

<!-- person -->
A passage a person owns. Leave it alone.
<!-- /person -->

## Open questions

### q1

- State: open
- Raised by: agent
- Attempts: 0
- Missing: Which component provides the package Acme.Logging.
- Waiting on: name Acme.Logging
- Answer looks like: A component whose provides list contains Acme.Logging, or a person stating it is public.
- Answer:

### Dismissed

- Whether PolySharp is a run-time dependency: no, it is build-time only.
```

- States are `open`, `needs-person`, `answered` and `dismissed`. `Raised by` is `cli`, `agent` or `person`.
- `Waiting on` is `repository <id>`, `name <provided name>`, `entry <id>` or `person`.
- Add questions with `cartographer question add`, which numbers them and refuses a duplicate. Do not type a question block by hand.
- The `Answer:` line is where a person types an answer. Everything after it, to the next `###`, is the answer.
- `### Dismissed` holds one line per dismissed question, saying what was dismissed and why, so nobody asks it again.

## Secrets

`check` rejects an entry containing something that looks like a credential: `password=`, `pwd=`, `secret=`, `token=`, `accountkey=`, `sharedaccesskey=` or `api_key=` followed by a value, or a private key header. Say that a credential exists and where (`config#L14`), never what it is.

## Worked example: a component

`repositories/finance-billing/components/acme-billing-api.md`, after the mechanical pass and an agent's work. The CLI wrote `provides`, `packages`, `verified`, the extracted block, and the links with basis `extracted`. The agent wrote the summary, both prose sections, `uses` and `count` on the `depends-on` link, the `inferred` links, and the question.

```markdown
---
kind: component
name: Acme.Billing.Api
type: service
summary: HTTP service that raises invoices, posts them to the ledger and records customer payments.
repository: repositories/finance-billing/repository
stack: [csharp, net8.0]
sources:
  config: finance-billing:src/Acme.Billing.Api/appsettings.json@1a2b3c4
  invoices: finance-billing:src/Acme.Billing.Api/Invoices/InvoiceService.cs@1a2b3c4
  payments: finance-billing:src/Acme.Billing.Api/Payments/PaymentHandler.cs@1a2b3c4
  proj: finance-billing:src/Acme.Billing.Api/Acme.Billing.Api.csproj@1a2b3c4
provides:
  - name: Acme.Billing.Api
    as: assembly
    basis: extracted
    source: proj#L4
packages:
  - "Serilog 3.1.1"
links:
  - type: depends-on
    to: repositories/platform-core/components/acme-data
    name: Acme.Data
    version: "4.2.0"
    uses: [CustomerStore, PaymentStore, SqlRunner]
    count: 9
    basis: extracted
    source: proj#L18
  - type: calls
    to: databases/billing/routines/dbo/usp_invoice_post
    how: sql
    basis: inferred
    source: invoices#L88
  - type: reads
    to: databases/billing/tables/dbo/customer
    via: repositories/platform-core/components/acme-data
    basis: inferred
    source: payments#L37
  - type: writes
    to: databases/billing/tables/dbo/payment
    via: repositories/platform-core/components/acme-data
    basis: inferred
    source: payments#L41
  - type: uses
    to: databases/billing/database
    basis: extracted
    source: config#L12
  - type: publishes-to
    to: channels/billing-events
    basis: inferred
    source: payments#L63
verified:
  commit: "1a2b3c4"
  date: "2026-11-21"
  cartographer: "0.1.0"
---

## Overview

The billing service is what other systems call to raise an invoice or record that a customer has paid. When an invoice is finalised it is posted to the ledger. When a payment arrives it is stored against the customer, and a message is published so that other systems can react to it.

It keeps its data in the Billing database. A change to how invoices or payments are stored there would affect this service.

## Technical detail

<!-- extracted -->
Target framework: net8.0. Output type: web application.
<!-- /extracted -->

- **Invoices.** `InvoiceService.Post` calls the stored procedure `dbo.usp_Invoice_Post` through `SqlRunner.Exec` from Acme.Data. `SqlRunner` is a pass-through helper: the procedure name is a literal at the call site (`invoices#L88`), so the link is made here.
- **Payments.** `PaymentHandler.Handle` looks the customer up with `CustomerStore.Find` and saves the payment with `PaymentStore.Save`. Both are Acme.Data entry points; the tables they touch are recorded on Acme.Data's entry and repeated here as links marked `via` it.
- **Messages.** After a payment is saved, a `PaymentReceived` message is published to the `billing-events` topic (`payments#L63`).
- **Configuration.** The connection string for Billing is in `appsettings.json` (`config#L12`). It carries a SQL login; the credential is in that file and is not copied here.
- Types used from Acme.Data were found by reading the usage candidates: 9 sites across `Invoices/` and `Payments/`.

## Open questions

### q1

- State: needs-person
- Raised by: agent
- Attempts: 0
- Missing: Which payment provider PaymentHandler sends refunds to. The address comes from the setting Payments:BaseUrl, which has no value in the repository.
- Waiting on: person
- Answer looks like: The name of the provider, or the environment's value of Payments:BaseUrl without any key.
- Answer:
```

What to notice:

- The Overview could be read by someone who has never opened the code. It names no class.
- Every sentence in Technical detail is backed by a link above it or a cited file. The refund provider is not mentioned in prose as a fact, because nothing supports it: it is a question.
- The two links reached through Acme.Data's entry points carry `via`. The call to the stored procedure does not, because the helper only passes the name through.

## Worked example: a routine

`databases/billing/routines/dbo/usp_invoice_post.md`. The CLI parsed the procedure body and wrote the name, the four `extracted` links and the parameters. The agent wrote the summary, the prose and one `inferred` link the parser could not see, because the table name is inside a string that is executed.

```markdown
---
kind: routine
name: dbo.usp_Invoice_Post
type: procedure
summary: Posts a draft invoice, writes one ledger row per invoice line and records the posting in the audit log.
database: databases/billing/database
sources:
  def: finance-billing-db:Billing/dbo/StoredProcedures/usp_Invoice_Post.sql@9f8e7d6
links:
  - type: calls
    to: databases/billing/routines/dbo/usp_audit_write
    how: sql
    basis: extracted
    source: def#L47
  - type: reads
    to: databases/billing/tables/dbo/invoiceline
    basis: extracted
    source: def#L18-L24
  - type: writes
    to: databases/billing/tables/dbo/invoice
    basis: extracted
    source: def#L31
  - type: writes
    to: databases/billing/tables/dbo/ledgerentry
    basis: extracted
    source: def#L36-L44
  - type: writes
    name: dbo.LedgerArchive
    database: BillingArchive
    basis: inferred
    source: def#L52-L58
verified:
  commit: "9f8e7d6"
  date: "2026-11-21"
  cartographer: "0.1.0"
---

## Overview

Posting is the step that makes an invoice final. This procedure marks a draft invoice as posted and writes a matching entry in the ledger for each line on it, so that the invoice and the accounts agree. Each posting is also noted in the audit log.

For invoices dated before the current financial year it also copies the ledger entries to the archive database.

## Technical detail

<!-- extracted -->
| Parameter | Type | Direction |
|---|---|---|
| @InvoiceId | int | in |
| @PostedBy | nvarchar(50) | in |
| @LedgerBatchId | int | out |
<!-- /extracted -->

Runs in one transaction. It reads the lines of the invoice from `dbo.InvoiceLine`, sets `Status` and `PostedOn` on `dbo.Invoice`, inserts one row per line into `dbo.LedgerEntry`, and calls `dbo.usp_Audit_Write`.

The archive copy (`def#L52-L58`) is built as a string and run with `sp_executesql`, which is why the mechanical pass did not find it. The string names `BillingArchive.dbo.LedgerArchive`. That database has no entry yet, so the link is unresolved.

Source: `def`.

## Open questions

### q1

- State: needs-person
- Raised by: agent

- Missing: Where the database BillingArchive is defined. This procedure writes to its table dbo.LedgerArchive, and no scanned repository or listed instance has a database of that name.
- Waiting on: person
- Answer looks like: The repository that holds its schema, or the instance it lives on so that it can be listed in cartographer.yml.
- Answer:
```

What to notice:

- The entry describes and points. It does not copy the procedure's body.
- The unresolved link gives the real name and a database hint instead of an invented ID. The CLI fills in `to` once the archive database has an entry.
- The question says exactly what is missing, what it waits on and what would settle it.
